Посилання на обидва Issues додано до `MykhailenkoTest.java`. Інші невдалі тести потребують окремої звірки з відповідними Issues та відповідальними учасниками команди.

Артефакти: протокол відтворення «з нуля», перелік слабких місць і питання до демо.
- SRS задає для власних unit-тестів трасування: UT-17→BL10, UT-18→BL40, UT-19→BL50, UT-20→BL70. За методичкою саме тестований метод, тестові значення й очікування мають бути пов'язані з кожним правилом/межею, а не лише позначені ID BL.

Також Issue #3 вказує очікування ≤3 с, тоді як переданий SRS P10 містить ≤50 мс; цю розбіжність потрібно уточнити у власника SRS.

## 3. План роботи АО

1. **Зберегти базову точку аудиту.** Зафіксувати URL репозиторію, гілку/commit SHA, дату, ОС, `mvn -v`, `java -version` і версію Chrome. Не змінювати тестовий код до збереження первинних логів.
2. **Чисте відтворення за README.** Клонувати в окрему порожню папку; виконати дві README-команди без додаткових параметрів. Зберегти результати запусків і `target/surefire-reports`.
3. **Перевірити власні UT-17–UT-20.** Зіставити кожен тест з відповідною вимогою та граничними значеннями. Для UT-17 та UT-19 зареєстровано Issues #12 і #13.
4. **Перевірити UI-07/UI-08.** Початковий повний прогін зафіксував тайм-аут UI-08. Після уточнення сценарію два окремі повторні запуски `MykhailenkoUiTest` завершилися успішно (2/2). Для висновку про весь UI-набір потрібен новий повний прогін.
5. **Незалежно перевірити трасованість.** Звірити покриття BL-вимог із матрицею, а тестові ID з реальними методами, анотаціями та Issues.
6. **Звірити дефекти.** Для кожного Issue перевірити вимогу, тест, severity/priority, кроки відтворення, expected/actual, докази та статус.
7. **Передати розбіжності відповідальним.** Surefire summary — КТ; coverage matrix та UI-сценарії — ТА; Selenium IDE файли — ІТ; статуси Task Board — відповідальному за дошку.
8. **Підготувати демо-рецензію.** Зібрати перелік слабких місць із доказами та питаннями для команди.
